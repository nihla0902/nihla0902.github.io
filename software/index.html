AquaPulse: river water-quality monitoring with a map-based website

A map-based website with an administrator login, backed by ESP32 firmware logic.

Tools

Status
Phase 1 complete: simulation and website prototype

The problem

Air-quality maps use colour so anyone can read them at a glance. River water quality is harder to find and harder to read. We wanted a monitoring network where a station's health shows up as one colour on a map, with the detail behind it for administrators.

What I did

  • Built the complete ESP32 simulation in Wokwi: sensor inputs, threshold logic, status grading, display and serial output.
  • Built part of the website with the team.

How it works

The station reads ten parameters: pH, turbidity, TDS, dissolved oxygen, chlorine, ammonia, nitrate, temperature (DS18B20), ORP and conductivity. In the simulation, potentiometers stand in for the analog probes, and ORP and conductivity are simulated values in the code.

Each reading is compared with its thresholds and graded normal, caution or danger. The station's overall status is its most severe grade. It appears on the TFT display and in the serial monitor.

On the website, each station is a coloured marker on a map. Administrators log in to a dashboard with station status, alerts and incidents, thresholds and registrations.

Result

The simulation shows all three system states, normal, caution and danger, on the display and in the serial output. The website prototype shows the map and the administrator dashboard in demo mode.

What I would improve

This is Phase 1. The sensors are simulated, and readings are not yet sent from a device to the website.

Next: connect real sensors, calibrate them, and send live readings to a database that feeds the map and the alerts.

Soil moisture monitor with a live web dashboard

A data path from sensor to Python script to Firebase to a live web dashboard.

The problem

Farmers and researchers need to know how wet the soil is without walking to the field to check. We wanted the reading to be visible from any browser.

What I did

  • Simulated the Arduino circuit before it was built.
  • Built part of the web dashboard with the team.

How the data moves

Data moves through four steps:

  1. The Arduino turns the raw sensor reading into a moisture percentage.
  2. A Python script (PySerial) on a connected computer reads the value over USB.
  3. The script writes each reading to Firebase Firestore with a server timestamp.
  4. The dashboard, written in HTML, CSS and JavaScript and hosted on Vercel, reads the data live. It shows a moisture gauge, a graph of the last hour, and whether the device is connected.

Result

On 12 September 2025 the dashboard tracked the moisture falling from about 93% to 39% over one hour.

Open the live dashboard

The page shows the last recorded readings. It says “Device disconnected” when the sensor script is not running.

What I would improve

The Arduino has to stay connected to a computer by USB. Next: an ESP32 with Wi-Fi so the sensor sends its own data, more sensors, and an alert when the soil is too dry.

Load flow analysis of a 3-bus power system in GNU Octave

A numerical solver in GNU Octave with plotted results.

The problem

Engineers need the voltage at every point of a network and the power lost in its lines, before the network is built or changed. The numbers come from nonlinear power equations, so a program has to solve them.

What I did

  • Entered the network data: three lines with resistance and reactance, one slack bus and two load buses.
  • Wrote the Y-bus matrix and the iterative solver in GNU Octave, a free MATLAB-compatible tool.
  • Calculated the line losses and plotted the voltage profile and the convergence curve.

How it works

Line data (per unit)
LineResistanceReactance
1–20.020.20
1–30.030.40
2–30.0250.25

Bus 1 is the slack bus at 1.05 per unit. Buses 2 and 3 are load buses drawing 0.8 + j0.3 and 0.5 + j0.2 per unit.

The solver starts from a flat voltage guess. At each step it calculates the real and reactive power at every bus, compares it with the scheduled load, and corrects the voltage angles and magnitudes by a small fixed step of 0.1, for up to 20 iterations.

I used this fixed-step correction instead of Newton-Raphson, which uses a Jacobian matrix to reach the answer in fewer iterations.

The maximum power mismatch fell from about 0.78 in the first iteration to close to zero by iteration 20, as the convergence plot shows.

Bus 3 ends with the lowest voltage, so it is the first place to look at for voltage support.

What I would improve

Next: replace the fixed step with a Jacobian-based Newton-Raphson solver, compare the two on iterations needed, and try a larger network.
